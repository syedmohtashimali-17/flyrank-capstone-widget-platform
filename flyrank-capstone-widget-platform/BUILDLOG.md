# Build Log

This document provides an honest account of the AI-assisted development process for the FlyRank Widget Platform.

## Project Goal

Build a complete embeddable lead-capture platform with:
- Multi-tenant widget management
- Cross-origin JavaScript embedding
- Secure submission handling with validation, rate limiting, and spam protection
- Geographic enrichment with fallback providers
- Background side effects with retry logic
- Analytics dashboard with tenant isolation
- Comprehensive automated testing

## Architecture Decisions

### Technology Stack Selection
**Decision**: FastAPI + SQLAlchemy + SQLite + Pydantic v2
**Reasoning**: 
- FastAPI provides excellent OpenAPI documentation and async support
- SQLAlchemy offers robust ORM with migration support via Alembic
- SQLite suitable for development/demo while allowing PostgreSQL migration
- Pydantic v2 provides strong validation and serialization

### Service Layer Architecture
**Decision**: Layered architecture with dedicated service classes
**Implementation**:
```
HTTP Router → Schema Validation → Service Layer → Repository/ORM → Database
```
**Benefits**:
- Clear separation of concerns
- Testable business logic
- Consistent error handling
- Easy to mock for testing

### Multi-Tenancy Strategy
**Decision**: Query-level tenant isolation using owner_id/tenant_id filters
**Implementation**: Every data access query includes tenant restriction
**Security**: 404 responses for cross-tenant access (no info leakage)

### Rate Limiting Approach  
**Decision**: In-memory rate limiting with dual dimensions (IP + Widget)
**Trade-offs**: Simple for development, would need Redis/shared store for production
**Implementation**: Time-window tracking with automatic cleanup

## Problems Encountered

### 1. Windows Command Line Issues
**Problem**: Directory creation commands failing with path errors
**Solution**: Used individual directory creation and file writing instead of complex shell commands
**Learning**: Cross-platform compatibility requires careful command selection

### 2. Async Context in Services
**Problem**: Mixing sync and async code in service layer
**Initial Approach**: All services synchronous
**Correction**: Made geo service async, handled properly in submission pipeline
**Lesson**: Plan async boundaries early in design

### 3. Database Session Management  
**Problem**: Session lifecycle in dependency injection
**Solution**: Proper session cleanup in FastAPI dependency system
**Pattern**: Used try/finally blocks for session cleanup

### 4. CORS Configuration Complexity
**Problem**: Balancing security with functionality for cross-origin requests
**Solution**: Explicit CORS configuration with proper preflight handling
**Security**: Avoided wildcard credentials, used specific headers

## Known Limitations

### Development-Focused Design
- **SQLite Database**: Single-file, not suitable for production scale
- **In-Memory Rate Limiting**: No shared state across instances
- **Simulated Side Effects**: No real email/webhook delivery
- **Basic Geo Providers**: Free tier limitations and timeouts

### Security Considerations
- **JWT Secret**: Must be rotated in production
- **CORS Origins**: Should restrict to known domains in production
- **Request Logging**: Could expose sensitive data if not configured properly
- **Side Effect Retries**: No exponential backoff limits (could retry indefinitely)

### Scalability Constraints  
- **Single Process**: No horizontal scaling support
- **File-Based Storage**: No distributed asset delivery
- **Background Jobs**: In-process, not queue-based
- **Database Connections**: Single connection pool
